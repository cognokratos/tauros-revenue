# REST API

The API is [JSON:API](https://jsonapi.org) generated by AshJsonApi from the
routes declared on the domains (`Tauros.Accounts`, `Tauros.Revenue`). There are
no controllers. The routes call the same actions, under the same policies, as
the UI. **Which interface you use never changes what you may do.**

- Base path: `/api/v1`
- Media type: `application/vnd.api+json`
- OpenAPI document: `GET /api/v1/open_api` · Swagger UI: `/api/swaggerui`
- Authentication: `Authorization: Bearer <credential>`, where the credential is
  either a human's sign-in token or an agent's API key

## Routes

### Accounts

| Method | Path | Action | Who may |
| --- | --- | --- | --- |
| POST | `/users/sign-in` | `User.sign_in_with_password` → `meta.token` | anyone |
| GET | `/agents`, `/agents/:id` | `Agent.read` | human (own agents) |
| POST | `/agents` | `Agent.create` → `meta.api_key` (once) | human |
| PATCH | `/agents/:id` | `Agent.update` (name) | human owner |
| PATCH | `/agents/:id/rotate-api-key` | `Agent.rotate_api_key` → `meta.api_key` | human owner |
| DELETE | `/agents/:id` | `Agent.destroy` (refused while it owns records) | human owner |

There is no registration route. Humans are invited (UI, `/invite`) or, for the
first approver, bootstrapped from a console ([WORKFLOWS.md](WORKFLOWS.md)).

### Customers and destinations

| Method | Path | Action | Who may |
| --- | --- | --- | --- |
| GET | `/customers`, `/customers/:id` | `Customer.read` | human (their agents'), agent (its own) |
| POST | `/customers` | `Customer.create` | human, for an agent they own |
| PATCH | `/customers/:id` | `Customer.update` (name, email) | human owner |
| DELETE | `/customers/:id` | `Customer.destroy` (refused while invoices use it) | human owner |
| GET | `/payment-destinations`, `/payment-destinations/:id` | `PaymentDestination.read` | human (their agents'), agent (its own) |
| POST | `/payment-destinations` | `PaymentDestination.create` | agent |
| PATCH | `/payment-destinations/:id/deactivate` | `PaymentDestination.deactivate` | agent (own) or owning human |

### Invoices

| Method | Path | Action | Who may |
| --- | --- | --- | --- |
| GET | `/invoices`, `/invoices/:id` | `Invoice.read` | human (their agents'), agent (its own) |
| POST | `/invoices` | `Invoice.create_draft` → `meta.idempotent_replay` | **agent** |
| PATCH | `/invoices/:id/revise` | `Invoice.revise` | **agent** (own) |
| PATCH | `/invoices/:id/submit` | `Invoice.submit_for_approval` | **agent** (own) |
| PATCH | `/invoices/:id/withdraw` | `Invoice.withdraw` | agent (own) or owning human |
| PATCH | `/invoices/:id/approve` | `Invoice.approve` | **human approver** (owner) |
| PATCH | `/invoices/:id/reject` | `Invoice.reject` | **human approver** (owner) |
| PATCH | `/invoices/:id/request-changes` | `Invoice.request_changes` | **human approver** (owner) |
| PATCH | `/invoices/:id/cancel` | `Invoice.cancel` | **human approver** (owner) |

The human-authority routes are reachable with an agent key, and they answer
`403`. They are not hidden; they are refused by policy, the same policy that
refuses the LiveView and direct Ash calls.

Invoices accept `?include=current_revision`, `revisions`, `approvals` and
`events`. A revision carries `number`, `customer_id`, `payment_destination_id`,
`currency`, `due_date`, `lines`, `total`, `reasoning`, `canonical_payload` and
`payload_hash`.

## Walkthrough

```bash
# 1. A human approver signs in (the seeds create demo@tauros.local).
TOKEN=$(curl -s -X POST localhost:4000/api/v1/users/sign-in \
  -H 'content-type: application/vnd.api+json' \
  -d '{"data":{"attributes":{"email":"demo@tauros.local","password":"tauros-demo-password"}}}' \
  | jq -r .meta.token)

# 2. The human registers an agent. meta.api_key is shown exactly once.
AGENT_KEY=$(curl -s -X POST localhost:4000/api/v1/agents \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/vnd.api+json' \
  -d '{"data":{"type":"agent","attributes":{"name":"Billing agent 2"}}}' \
  | jq -r .meta.api_key)
AGENT_ID=$(curl -s localhost:4000/api/v1/agents -H "authorization: Bearer $TOKEN" \
  | jq -r '.data[] | select(.attributes.name=="Billing agent 2") | .id')

# 3. The human registers a customer for that agent.
CUSTOMER=$(curl -s -X POST localhost:4000/api/v1/customers \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/vnd.api+json' \
  -d '{"data":{"type":"customer","attributes":{"name":"Initech","email":"ap@initech.example","agent_id":"'$AGENT_ID'"}}}' \
  | jq -r .data.id)

# 4. The agent registers where it gets paid: USDC on Arbitrum.
DESTINATION=$(curl -s -X POST localhost:4000/api/v1/payment-destinations \
  -H "authorization: Bearer $AGENT_KEY" -H 'content-type: application/vnd.api+json' \
  -d '{"data":{"type":"payment_destination","attributes":{
        "label":"Treasury (Arbitrum)","currency":"USDC","network":"arbitrum",
        "address":"0x5aAeb6053F3E94C9b9A09f33669435E7Ef1BeAed"}}}' \
  | jq -r .data.id)

# 5. The agent proposes an invoice, retry-safe, and submits it.
INVOICE=$(curl -s -X POST localhost:4000/api/v1/invoices \
  -H "authorization: Bearer $AGENT_KEY" -H 'content-type: application/vnd.api+json' \
  -d '{"data":{"type":"invoice","attributes":{
        "idempotency_key":"initech-2026-10","customer_id":"'$CUSTOMER'",
        "payment_destination_id":"'$DESTINATION'","currency":"USDC","due_date":"2099-01-31",
        "lines":[{"description":"Monthly retainer","quantity":"1","unit_amount":"1200"}],
        "reasoning":"Retainer per the signed agreement of 2026-09-12."}}}' \
  | jq -r .data.id)

curl -s -X PATCH localhost:4000/api/v1/invoices/$INVOICE/submit \
  -H "authorization: Bearer $AGENT_KEY" -H 'content-type: application/vnd.api+json' \
  -d '{"data":{"type":"invoice","id":"'$INVOICE'","attributes":{}}}' | jq .data.attributes.state
# "pending_approval"

# 6. The human reads the exact revision and approves it by id and hash.
read REVISION HASH < <(curl -s "localhost:4000/api/v1/invoices/$INVOICE?include=current_revision" \
  -H "authorization: Bearer $TOKEN" | jq -r '.included[0] | "\(.id) \(.attributes.payload_hash)"')

APPROVE='{"data":{"type":"invoice","id":"'$INVOICE'","attributes":{"revision_id":"'$REVISION'","payload_hash":"'$HASH'"}}}'

# The agent cannot do this itself:
curl -s -X PATCH localhost:4000/api/v1/invoices/$INVOICE/approve \
  -H "authorization: Bearer $AGENT_KEY" -H 'content-type: application/vnd.api+json' -d "$APPROVE" | jq '.errors[0].status'
# "403"

curl -s -X PATCH "localhost:4000/api/v1/invoices/$INVOICE/approve?include=approvals" \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/vnd.api+json' -d "$APPROVE" \
  | jq '{state: .data.attributes.state, approval: .included[0].attributes | {decision, payload_hash}}'
```

## Errors

Errors are JSON:API error objects. Validation errors point at the offending
attribute:

```json
{
  "errors": [
    {
      "status": "400",
      "code": "invalid_attribute",
      "detail": "must be an IBAN in electronic format (no spaces) with a valid checksum",
      "source": { "pointer": "/data/attributes/address" }
    }
  ]
}
```

| Status | Meaning |
| --- | --- |
| 400 | invalid or unknown input: a missing field, a value that breaks a rule, or an attribute no action accepts (`state`, `agent_id`, `total`…) |
| 401 | no valid credential (`unauthorized`) or failed sign-in (`invalid_credentials`) |
| 403 | authenticated, but a policy forbids the action |
| 404 | the record does not exist *or is not visible to you* (also for PATCH and DELETE) |
| 409 | the command conflicts with what already happened; `code` says which |

| 409 `code` | When |
| --- | --- |
| `idempotency_conflict` | the idempotency key was already used by this agent for a different payload |
| `invalid_transition` | the state machine has no such move from the invoice's current state |
| `stale_revision` | the decision names a revision that is no longer current |
| `payload_mismatch` | the decision's hash is not the revision's hash |
| `already_decided` | the revision already has a (different) decision |
| `destination_inactive` | approval of a revision whose destination has been retired |
| `payload_integrity` | the revision no longer matches its sealed payload |

Lists are unsorted unless you ask: use JSON:API sorting, e.g.
`GET /api/v1/invoices?sort=-updated_at`.

## Changes in the learning phase (breaking)

There are no external consumers yet; correctness was preferred over
compatibility.

| Old contract | New contract | Why | Migrating |
| --- | --- | --- | --- |
| `/api/v1/wallet-accounts`, type `wallet_account` | `/api/v1/payment-destinations`, type `payment_destination` | a destination can be an IBAN; "wallet" was wrong | change the path and type |
| attributes `wallet_name`, `public_address`, `currency` | `label`, `address`, `currency`, **`network`** (required) | a currency does not decide the network (USDC is on several) | send `network`; existing rows were backfilled with the network their currency implied (BTC → `bitcoin`, fiat → `iban`, others → `ethereum`) |
| shape-only address checks | IBAN mod-97 and Taproot bech32m checksums | catch typos | addresses that were accepted before may now be rejected on create; stored ones are not re-validated |
| destinations could not change at all | they still cannot, but gain `state` and `PATCH …/deactivate`; corrections use `supersedes_id` | stop using a destination without deleting it | — |
| `GET /customers` was human-only | agents can read their own customers | an agent must address a proposal to its customer | — |
| `/register` and magic-link registration | removed; humans are invited or bootstrapped | strangers must not become approvers | existing users became operators; designate an approver once with `bootstrap_approver` |

## Changes from the pre-Ash API

| Before | Now |
| --- | --- |
| `POST /api/admin/v1/login` → `{data: {token: "Bearer …"}}` | `POST /api/v1/users/sign-in` → `meta.token` |
| `POST /api/admin/v1/agents` with an admin-chosen `api_key` | `POST /api/v1/agents`; Tauros generates the key and returns it once in `meta.api_key` |
| `/api/admin/v1/customers[/:id]` | `/api/v1/customers[/:id]` |
| `POST /api/v1/accounts` with `X-API-KEY` | `POST /api/v1/payment-destinations` with `Authorization: Bearer <api key>` |
| Bodies nested under `agent`/`customer`/`account` | JSON:API `data.attributes` |
| `{error: {code, message, details}}`, 422 for validation | JSON:API `errors[]`, 400 for validation |
| Agent-not-owned on customer create: 422 | 403 |
| `DELETE` → 204 | `DELETE` → 200 with the deleted resource |
| `/api/v1/test`, `/api/admin/v1/test` | removed |
